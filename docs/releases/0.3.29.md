# umkim-thin 0.3.29

Patch release: the installer left the host storage agent running the previous
release's binary, found while applying 0.3.28 to the production single node.

## Fixed

**An upgrade never restarted `umkim-thin-storage`.** `install_storage_agent`
extracts the new `umkim-thin` binary over `/usr/local/bin/umkim-thin` and then
runs `systemctl enable --now umkim-thin-storage.service`. On a first install
that starts the unit; on an upgrade the unit is already active, so `--now` is a
no-op and the process keeps its original file descriptor:

```
$ ls -l /proc/<pid>/exe
/proc/<pid>/exe -> /usr/local/bin/umkim-thin (deleted)
```

The host agent — the thing that owns disks, RAID and host NFS exports — then
runs the code from whichever release was installed first, for the life of the
node. Nothing reports it: the unit is `active`, the socket answers, and the
console's storage calls work, so only `--doctor` or poking at `/proc` shows it.

The installer now restarts the unit when it is already active and enables it
otherwise. `ci/static.sh` fails if the restart disappears, because "the unit is
active" is exactly what makes the bug invisible.

## Verification

- `ci/static.sh` passes, including the new guard; reintroducing the old
  `enable --now` makes it fail with the reason.
- On the production single node, 0.3.28 left the agent on a deleted binary and
  0.3.29's logic restarts it: after the restart `/proc/<pid>/exe` points at the
  live `/usr/local/bin/umkim-thin`, the unit is active and the socket listens.
- The same run carries `--doctor`'s fix from 0.3.28: *All checks passed*,
  including "5 app data volumes readable".

## Upgrade notes

No state or value change. `sudo ./install.sh --reuse-k3s` is enough; the agent
is restarted as part of it. Nothing else changed from 0.3.28.
