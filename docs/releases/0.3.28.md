# umkim-thin 0.3.28

The media stack's qBittorrent queue limits become install-time settings, and
`install.sh --doctor` stops dying before it can report anything.

## Why the queue limits

Three approved requests sat at *Requested* for ever on the production install.
Nothing was broken: Seerr had sent them to Radarr, Radarr had them, and
qBittorrent listed them as `queuedDL`. The queue, not the request path, was the
bottleneck.

qBittorrent's active limits were its own defaults (`max_active_torrents = 5`,
`6/3` down/up), and **five dead torrents held every slot**. They had no seeders
and had not moved a byte in eleven days, but a torrent with no connections still
counts as "active", so nothing else could start. Seerr reported *Processing*
because nothing had downloaded - a true report, not a status bug.

Raising the limits and clearing the dead torrents started all three downloads
immediately; one was followed to completion (qBittorrent 100 % -> Radarr
`hasFile=true` -> Jellyfin scan -> Seerr fired `MEDIA_AVAILABLE`).

## Added

- **`bootstrap.qbittorrentLimits`** on the servarr chart (`0.3.9`):
  `maxActiveTorrents` (300), `maxActiveDownloads` (100), `maxActiveUploads`
  (100) and `dontCountSlowTorrents` (true). Rendered as
  `QBITTORRENT_MAX_ACTIVE_*` into the bootstrap ConfigMap.
- **The console's Servarr install form** grows those four fields, and
  `GET`/`POST /api/apps/servarr/settings` carry them. The panel offers the
  shipped defaults for a reset.
- **CLI:** `--qbittorrent-max-torrents`, `-max-downloads`, `-max-uploads` and
  `--qbittorrent-dont-count-slow` on `app install`/`plan`/`validate` and on
  `servarr settings`. Omitting them stays distinguishable from setting them, so
  an upgrade keeps the operator's stored values.

## Fixed

- **A limit of 0 is refused.** qBittorrent reads 0 as "no torrents active", so
  accepting it would have stopped every download silently. A per-direction
  limit above the total is refused too, because qBittorrent applies them
  *within* `max_active_torrents` and the setting would be unreachable.
- **The bootstrap compares every value it owns**, not just the save path. It
  would otherwise tell an install that predates the limits "already configured"
  and leave it wedged at 5/6/3.
- **An explicit `false` no longer renders as `true`.** The ConfigMap used
  sprig's `default`, which treats `false` as empty, so choosing "count every
  torrent, including stalled ones" silently did the opposite. It renders from
  key presence now, and `ci/static.sh` fails if `false` comes back as `true`.
- **`install.sh --doctor` aborted on every healthy install**
  (`r1: unbound variable`). One `local a=... b=${a...}` declares every name
  before assigning any, so the expansion hit an unset variable under `set -u`.
  The app-data-volume check — the section that proves a volume is readable — is
  what crashed, so the doctor printed a partial report and exited 1. It is now
  one `local` per name.

## Compatibility and upgrade safety

No state or value migration. An existing release that does not carry
`bootstrap.qbittorrentLimits` reads back as the shipped defaults (never zero),
and a bootstrap run re-applies them; if the live values already match, it is a
no-op.

Platform:

```bash
git pull && git submodule update --init --recursive
sudo ./install.sh --reuse-k3s
```

The new chart reaches an installed stack through the catalog: either re-run the
installer (which packages it into the mirror) and upgrade the app, or upload the
0.1.9 catalog and use **Applications → Upgrade**.

For an install that is already wedged, upgrading the chart is not enough — the
dead torrents still hold the slots. Remove the stalled ones (qBittorrent's
**Stalled** filter, or `POST /api/v2/torrents/delete` with
`deleteFiles=false`), or set `dont_count_slow_torrents=true`, which the new
default does.

## Verification

- `ci/static.sh` passes, including a new guard that renders the ConfigMap with
  `dontCountSlowTorrents=false` and fails if it comes back `true`.
- `go test ./...` passes, with tests for zero/negative/inverted limits, for
  reading a release that predates the setting (defaults, not zero), and for the
  flags distinguishing "omitted" from "set".
- The bootstrap was run against the live qBittorrent: limits applied from the
  environment (`250/90/80`), the shipped `300/100/100` restored, and a second
  run correctly reported "already configured" instead of rewriting.
- `install.sh --doctor` on the production single node: *All checks passed*,
  including "5 app data volumes readable".
