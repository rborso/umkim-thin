# umkim-thin 0.3.16

Patch release: two defects found by manually exercising the apps as a real
tenant on both lab environments, plus the test that would have found the first
one.

## What the manual pass covered

Both clusters (dev-single and ha-dev, 0.3.15, all ten app groups) were driven as
an **invited regular tenant** - a fresh directory user with no local account in
any app - rather than as an administrator:

- Gitea: create a repository over the API as the tenant, read it back, confirm
  the owner is the directory identity.
- Nextcloud: upload a file, read it back, and see it in a PROPFIND listing.
- Paperless / Immich / Mealie / HomeBox / SparkyFitness: complete the real SSO
  round trip as the tenant, then call the app's own API.
- Sonarr / Radarr / Prowlarr / qBittorrent / Jellyfin: load the UI through the
  portal without an authorization loop.

The deep client journeys (28 on ha-dev, 36 on dev-single) were run as well.

## Fixed

**`ci/portal-user.sh` could abort an entire run on a healthy portal.** It built
the login check as

```sh
code=$(curl ... -w '%{http_code}' ... || echo 000)
```

`curl` can print the status and still exit non-zero. On dev-single it returned
`401` and exited **23** ("client returned ERROR on write" - the response body
went to a fixed `/tmp/verify.out` that an earlier root-owned run had left
unwritable), so `code` became `401000`. The caller compared that to `200`,
concluded the portal was unreachable, and stopped with

```
could not verify the login for ci-portal-... (HTTP 200000); not touching the account.
```

`ci/lib.sh` now provides `http_code()`, which keeps curl's output and treats
anything that is not three digits as `000`. Every `|| echo 000` in `ci/` was
converted: `cleanup-ci.sh`, `backup-restore.sh`, `faults.sh` and `vpn-check.sh`
had the same latent `200000`, which their `case` lists would have reported as a
false failure. The login check no longer needs the body at all.

**The identity CronJob could wedge itself permanently.** `lldap-managed-groups-sync`
runs with `concurrencyPolicy: Forbid`. On dev-single a Job from **30 hours
earlier** was still `active` because no node had 32Mi to schedule it (the node
sits at 99% of memory requests once every app is installed), so every later tick
was skipped: the managed groups had not been reconciled since the day before.
Deleting it just produced another stuck Job a few minutes later.

`activeDeadlineSeconds: 300` is now set on the shared job spec, so a failed
attempt is retired and replaced on the next tick. Proven against the live
CronJob: a Job created from the patched template failed with
`DeadlineExceeded` at 5m07s and the following ticks proceeded. Chart
`identity` 0.1.12 -> 0.1.13.

## Added

**`tests/playwright/journeys/tenant.spec.ts`, in the gate.** No test asked
whether an invited tenant can *use* the apps: `auth.spec.ts` proves they can
authenticate, and the client journeys run as each app's own admin, which exists
regardless of the directory mapping. Shallow per app, as the tenant: the
workflows listed above. Added to the gating suites in `ci/e2e.sh` and
`ci/test-existing.sh`.

## Gate results

| | dev-single | ha-dev |
|---|---|---|
| Acceptance gate | 71 expected / 0 unexpected | 71 expected / 0 unexpected |
| Client journeys | 36 expected / 0 unexpected / 0 flaky / 1 skipped | 28 / 0 unexpected / 1 flaky |
| Tenant journeys (new) | 8/8 | 8/8 |

The one skipped journey is the Mealie -> SparkyFitness integration, which
`--journeys` disables by design (`--integrations` enables it). The one flaky
ha-dev journey was paperless OCR indexing timing out once and passing on retry.

## Known, not fixed

dev-single runs at **99% of memory requests** (6940Mi of ~7000Mi) with all ten
apps installed, so any additional platform pod - including the identity
reconcile - can only schedule when something else is evicted or scaled down.
The charts use `Recreate`, so an upgrade does not need surge capacity and is not
affected; the fix here means a starved reconcile now fails visibly and retries
instead of blocking silently. Sizing the single-node profile is a separate
change.
