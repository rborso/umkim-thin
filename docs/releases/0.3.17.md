# umkim-thin 0.3.17

Patch release: the platform charts could never retire an old version from the
chart mirror. Found verifying 0.3.16 on dev-single, where the mirror came up with
24 packages instead of 23.

## Fixed

**Both mirror pruners kept a platform chart by name, not by version.** 0.3.15
introduced the rule that stops the platform charts (`identity`, `umkim-thin`,
`wireguard-gateway`) being pruned - they are installer-owned and absent from the
catalog - but implemented it as "keep every tarball whose name starts with the
chart". So a version was never retired:

```
identity-0.1.12.tgz   identity-0.1.13.tgz
```

Bumping `identity` to 0.1.13 for 0.3.16's managed-groups fix surfaced it. Each
platform-chart bump would add a file for ever, creeping toward the 1 MiB
ConfigMap cap that seeds the mirror - the same class of failure as the original
"metadata.annotations: Too long".

- `install.sh` keeps the platform chart version this tree packages (read from each
  chart's `Chart.yaml`) instead of every version by prefix. It still never drops a
  platform tarball the run itself produced.
- `prune-chart-mirror.py` takes the staged artifacts directory as a third
  argument and keeps the catalog versions plus exactly what the run staged. The
  console role passes it.

## Guard

`ci/static.sh` now runs both pruners against a mirror holding superseded platform
versions and fails if either leaves one behind or drops a current one. The
existing budget check could not catch this: it packages one version per chart, so
it never sees accumulation.

Verified the guard bites: restoring the old prefix rule makes it fail with
`stale=3 platform=6 (expected 0 and 3)`.

## Verification

- `ci/static.sh` and `go test ./...` pass.
- Both pruners, run on a mirror with extra platform versions, settle on the same
  23 packages as a clean packaging run.
- dev-single re-installed: mirror back to 23 packages with only
  `identity-0.1.13`, 0 unhealthy pods; acceptance gate 79 passed (including the
  8 tenant checks).
