# umkim-thin 0.3.6

Seerr keeps its configuration on the PVC, and app upgrades preserve the
immutable storage settings of an existing release.

## Changed

### Servarr: Seerr data is persistent

- The servarr chart (**0.3.3**) sets Seerr's `CONFIG_DIRECTORY=/config`, so its
  SQLite database, settings and logs live on the `seerr-config` PVC instead of
  the container layer. The pod also gets `fsGroup: 1000` so a root-owned PV
  (Longhorn) is writable by the image's unprivileged `node` user.
- This fixes the Seerr banner **“The /app/config volume mount was not
  configured properly”**: it was accurate. Before 0.3.3 every Seerr restart or
  reschedule reset the app to first-run setup.
- `ci/static.sh` now asserts the rendered Seerr deployment sets
  `CONFIG_DIRECTORY=/config` and `fsGroup: 1000`.

### Console: immutable storage settings survive upgrades

- An upgrade now copies the previous install's `storageClass` **and**
  `accessMode` values from the **last deployed** Helm revision. Bound PVC
  storage classes and access modes are immutable, so re-rendering them from the
  current site default made Helm fail with:

  ```
  cannot patch "servarr-media" ... spec is immutable after creation
  ```

  The previous code preserved only `storageClass`; a single-node site that had
  switched its media default from `ReadWriteMany` to `ReadWriteOnce` hit this on
  every Servarr upgrade.
- Reading the last **deployed** revision matters after a failed upgrade: the
  latest revision may be the failed or pending one, whose values are not what
  the workload is running with.

## Compatibility and upgrade safety from 0.3.5

There are no console state, database or backup-manifest migrations.

**Servarr/Seerr:** an existing Seerr install kept its configuration in the
container's `/app/config`, not on the PVC. A pod restart or reschedule before
this release already discarded it; the bootstrap Job's earlier setup may
therefore need to run again. Before upgrading Servarr, copy the **current**
running container's data to the PVC:

```bash
kubectl -n servarr exec deploy/seerr -- sh -c \
  'cp -r /app/config/. /config/ && rm -f /config/DOCKER'
```

Do not copy the `DOCKER` sentinel: its absence is what tells Seerr the config
directory is now a proper volume. If the app has no important state, skipping
the copy is harmless; the console's **Applications → Setup** (or
`umkim-thin app setup servarr`) re-runs the idempotent bootstrap afterwards.

Existing `servarr-media` PVCs keep their original class and access mode during
the upgrade. A release left in `failed` or `pending-rollback` by the old
behaviour can be upgraded directly (or rolled back to its last deployed
revision) once the console is on 0.3.6.

Take a platform backup or VM snapshot first.

## Upgrade

Single node:

```bash
git fetch --tags
git checkout v0.3.6
git submodule update --init --recursive
sudo ./install.sh --reuse-k3s
```

Provisioned/HA cluster (on the jumphost, prefix with `CI_ON_JUMP=1`):

```bash
git fetch --tags
git checkout v0.3.6
git submodule update --init --recursive
PROVISION_ENV=deploy/provision-ha.env ./deploy/provision.sh
```

Then upgrade the app release from the console's **Applications** view (or
`umkim-thin app upgrade servarr --to 0.3.3`).
