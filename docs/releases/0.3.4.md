# umkim-thin 0.3.4

Home-page and console improvements, plus the Vaultwarden app with SSO-only
Authelia/LLDAP access.

## Changed

- **Home page:** the Servarr stack is split into **Jellyfin** (watch) and
  **Seerr** (request) cards. The page follows the browser language (English and
  Hungarian; other languages fall back to English).
- **Console:** dark mode is the default, with a persisted **Light mode** toggle;
  the login page follows the saved theme.
- **Vaultwarden:** new chart **0.1.2**, app **1.37.5**.
  - Authelia OIDC SSO with LLDAP users; `SSO_ONLY=true`.
  - Local Vaultwarden signup/password login is disabled.
  - The first SSO login creates the Vaultwarden account; the user still sets
    the client-side master password and vault key.
  - The chart builds the platform CA bundle and points the app at Traefik for
    OIDC discovery/token exchange, including on the HA lab-CA path.
  - `/admin` remains server management behind `ADMIN_TOKEN`; it cannot decrypt
    vaults.
- **Charts index:** `charts/apps/README.md` publishes chart and app versions.
- Added the Vaultwarden user journey: SSO, first master-password setup, secure
  note, new session SSO, master-password unlock, item decryption.

## Compatibility and upgrade safety from 0.3.3

The **platform** update is safe: there are no console state, backup, trusted
access, catalog storage or configuration migrations. The home page and console
theme are additive.

**Charts:** only Vaultwarden is new/changed. All other chart versions are
unchanged from 0.3.3 (`servarr` 0.3.2, `gitea` 0.1.21, and so on), so there is
no mass chart upgrade. The platform 0.3.4 pins the chart submodule with the
Vaultwarden 0.1.2 chart.

**Vaultwarden caveat:** v0.3.3 did not contain Vaultwarden, so a normal
0.3.3 → 0.3.4 update has no Vaultwarden data or users to migrate. A fresh
Vaultwarden install is SSO-only.

If you installed the intermediate Vaultwarden 0.1.0/0.1.1 local-login build,
its PVC and vault data survive the chart upgrade, but the 0.1.2 catalog defaults
(`SSO_ONLY=true`, `SIGNUPS_ALLOWED=false`, `SSO_SIGNUPS_MATCH_EMAIL=false`)
do **not** carry existing local accounts into SSO. To migrate them, temporarily
set `sso.only=false` and `sso.matchEmail=true` (only when the Authelia/LDAP email
matches the existing Vaultwarden account), verify the SSO login links the right
account, then set `sso.only=true`. Otherwise export the old vault and recreate it
under the SSO account.

Native clients must support the Vaultwarden OIDC flow before SSO-only access is
enforced; the web vault is covered by the journey. If a client does not, keep
`sso.only=false` (or use the web vault) rather than locking it out.

## Upgrade

Single node:

```bash
git fetch --tags
git checkout v0.3.4
git submodule update --init --recursive
sudo ./install.sh --reuse-k3s
```

Provisioned/HA cluster (on the jumphost, prefix with `CI_ON_JUMP=1`):

```bash
git fetch --tags
git checkout v0.3.4
git submodule update --init --recursive
PROVISION_ENV=deploy/provision-ha.env ./deploy/provision.sh
```

The Vaultwarden app is an optional catalog install; it is not added to an
existing single install automatically.
