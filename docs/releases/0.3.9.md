# umkim-thin 0.3.9

Correctness and durability: uninstall no longer destroys data, installs no
longer mutate (or leak through) the live catalog, and the gates now fail on the
classes of defect that let the November storage fault and the stale catalog go
unnoticed.

## Fixed

- **Uninstall without purge deleted the data.** `helm uninstall` removed every
  chart-rendered PVC (the charts render them inline) and the generated
  credential Secret, and the storage class then reclaimed the bytes — while the
  console offered "Uninstall" vs "Uninstall **and delete its data**". Every app
  PVC and generated Secret now carries `helm.sh/resource-policy: keep`; a
  reinstall adopts the kept objects, keeps the same database password and reads
  the existing data. `purge` still deletes the namespace and everything in it.
  The uninstall response (and the CLI) now names the volumes that were kept.
- **An install could rewrite the live catalog.** `renderValues` rendered the
  entry's nested maps in place, and the store hands out shallow copies, so the
  generated `sso.clientSecret` / `postgres.password` were written into the
  snapshot that `GET /api/catalog` serves, and a second install with different
  options reused the first render. `renderValues` deep-copies the values first.
- **The login limiter trusted a spoofable header.** It bucketed on the first
  `X-Forwarded-For` entry, so a client could pick a fresh bucket per request and
  brute-force the login. It now derives the bucket from the proxy chain (the
  immediate peer must be a proxy address, then the rightmost public hop), and
  the failure map is pruned so many source addresses cannot grow it without
  bound.
- **HA ran without `--request-timeout=1h`.** The flag was nested under the
  optional `secrets-encryption` block in the k3s config template, and HA runs
  with encryption off, so a large volume restore through the API was cut at the
  60-second default. The flag is unconditional again, and the live value is
  asserted.
- **Phantom catalog versions.** `versions[]` listed mealie 0.1.5/0.1.2,
  sparkyfitness 0.1.2, vaultwarden 0.1.1/0.1.0 and wireguard 0.1.2/0.1.1, none
  of which was ever committed to a chart. A fresh install picks one, misses the
  mirror tarball and hands Helm a GitHub tree URL. They are removed.
- **The default backup mode captured nothing on the beginner storage.**
  `snapshot` was the default, so on local-path/NFS the schedule produced a
  metadata-only archive. `auto` (snapshot where possible, file-copy the rest)
  is now the default, and the check fails when an archive carries no data.
- **Re-running `install.sh` reset the directory base DN.** `BASE_DN` was
  hardcoded and not preserved on a re-run, so an upgrade rewrote
  `UMKIM_THIN_BASE_DN` while LLDAP kept serving the original subtree; every app
  then pointed at a DN the directory does not serve and directory login broke.
  The stored value is reused, `--base-dn` is the deliberate override, and the
  default applies only to a first install.
- **A reinstall tried to change an immutable PVC.** `preserveImmutableStorage`
  only ran when the caller set the upgrade flag, but a plain `app install`
  against an existing release is the documented reinstall path (uninstall now
  keeps the data). Helm then tried to replace a bound claim's
  `storageClassName`/`accessMode` and the release failed with *"spec is
  immutable after creation"*. The preservation runs on every install and is a
  no-op when there is no previous release.
- `apps-state.json` was a read-modify-write with no lock and a plain
  `WriteFile`; two concurrent installs could lose each other's contribution and
  a crash could truncate the file. It is now serialised and written
  temp-then-rename.
- The job store never evicted finished jobs, and `start()` returned a snapshot
  after releasing the lock (a real data race, caught by `-race`). The history is
  capped at 100 and the snapshot is taken under the lock.
- `kubectl`/`helm`/storage/backup calls had no timeout, so a hung call could
  hold a request or a job goroutine forever (including the console login). They
  are bounded with a context now.
- A catalog upload removed the live directory before renaming the new one in;
  a crash or a cross-mount rename left the console with no catalog. It stages a
  sibling, swaps, and restores the old directory on failure.

## Added

- **Kubelet image GC and eviction thresholds** on both install paths  (`image-gc-high/low=70/60`, hard/soft eviction, `system-reserved`). The
  defaults let app upgrades keep every layer of every replaced tag: dev-single
  reached 51 GB of containerd images before this was cleaned by hand.
- `ci/uninstall-check.sh single|ha` — writes a marker, uninstalls without purge,
  asserts the claim, the bytes and the generated Secret survived, reinstalls and
  reads the marker again.
- `ci/faults.sh --k3s-restart` / `--k3s-crash` — restarts or `SIGKILL`s the k3s
  service on a live node. That is the failure that faulted the Longhorn volumes
  in November; a VM power-off does not reproduce it. Both scenarios wait for the
  data markers and every replica to rebuild.
- `ci/static.sh` guards: every app PVC and Secret keeps data on uninstall, every
  catalogued version exists in the chart history, the k3s `request-timeout` is
  not conditional, and both install paths set the kubelet thresholds.
- `ci/assert.sh` checks the live apiserver's `--request-timeout`.
- `ci/portal-user.sh` verifies the account can actually log in and removes a
  stale test account that a previous run left with a different password (the
  redemption refuses to take an account over, so this used to surface as a mass
  login failure for the whole run).

## Catalog release 0.1.4

The uninstall-keep change is a chart change, so it needs a chart release to
reach an installed cluster. Every app chart gets a patch bump
(`charts/apps` `6b1d253`) and the catalog adds the matching entries:

| app | chart | app | chart |
|---|---|---|---|
| actualbudget | 0.1.3 | nextcloud | 0.1.22 |
| gitea | 0.1.23 | paperless | 0.1.15 |
| homebox | 0.1.2 | servarr | 0.3.5 |
| immich | 0.1.13 | sparkyfitness | 0.1.4 |
| mealie | 0.1.7 | vaultwarden | 0.1.3 |

`catalog/VERSION` is `0.1.4`. `ci/static.sh` now fails when a template changed
without a `Chart.yaml` bump, which is how the fix would otherwise have been
silently undeliverable.

A follow-up servarr 0.3.6 (catalog **0.1.5**) rolls Jellyfin when the directory
bind password changes: the pod's checksum annotation hashed the rendered LDAP
ConfigMap, which carries only the `${LLDAP_BIND_PASSWORD}` variable name, so a
rotated password left the pod binding with the old one.

## Gate results

- `ci/static.sh` passes, including the four new guards (uninstall keeps data,
  catalogued versions exist, `request-timeout` unconditional, kubelet
  thresholds, and a chart change without a version bump).
- dev-single, full acceptance gate after re-provisioning to the new image:
  `apps.spec.ts` 42/42, `auth.spec.ts` 8 passed / 1 skipped, `tls`/`console`/
  `home` 20/20, `ci/assert.sh` PASSED, `ci/uninstall-check.sh` passed (volume,
  bytes and Secret kept across uninstall and reinstall).
- ha-dev, upgraded in place from 0.3.8 to 0.3.9 / catalog 0.1.4 and then run
  through `ci/test-existing.sh ha --pin`: **platform conformance PASS,
  application gate PASS, 71 expected / 0 unexpected / 0 flaky**. All ten apps
  moved to the bumped charts; all 27 app PVCs carry the keep annotation; 0
  unhealthy pods, 0 non-healthy Longhorn volumes.
- The gate found the base-DN regression end to end: after the fix, Gitea and
  Jellyfin LDAP login and Nextcloud's `ldap:test-config` pass again.
- `ci/faults.sh --k3s-restart` and `--k3s-crash` pass on dev-single with the
  data markers intact.
- `ci/backup-check.sh` reports 26 volumes captured as file copies under the
  `auto` default.

## Notes from the upgrade

- A Jellyfin LDAP failure seen during the ha-dev upgrade was an artefact of a
  hand-built Playwright invocation (a stale `apps.json` pointing at the other
  zone and a reused portal user), not a cluster defect: Jellyfin and LLDAP
  authenticate the directory user correctly on both clusters, and the gate
  passes when run through `ci/test-existing.sh`. Use that (or `ci/e2e.sh`)
  rather than driving the specs by hand.
- `ci/portal-user.sh` no longer deletes an account when the login check itself
  cannot reach the portal (a 403 from the public address, or 000). It removes a
  stale account only on a definite 401, so a runner without the zone pinned to
  the VIP fails with an actionable message instead of destroying a working
  account.

## Known gap

- `ci/assert.sh`'s live `--request-timeout` check reads the k3s journal, so it
  needs the node's journal retained since the last start. `ci/static.sh` also
  asserts the template, which is what catches a regression before it ships.
